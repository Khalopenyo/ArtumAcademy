# Workflow — как работать над задачами

## Цикл

```
ПОНЯТЬ → УТОЧНИТЬ → СПЛАНИРОВАТЬ → СОГЛАСОВАТЬ → СДЕЛАТЬ → ПРОВЕРИТЬ → ЗАКОММИТИТЬ
```

Пропустить можно только "уточнить", если задача абсолютно ясна. Остальные обязательны.

---

## 1. Понять задачу

Прочитай задачу полностью. Если есть ссылки на ТЗ, баг-репорты или дизайн — открой и посмотри.

Спроси себя:
- Какой пользовательский результат должен получиться?
- Какие модули системы затронет?
- Это новый функционал или изменение существующего?
- Есть ли похожий код в проекте, на который можно опереться?

## 2. Уточнить (если есть сомнения)

**Лучше задать вопрос, чем переписывать.** Спроси пользователя, если:
- Непонятен бизнес-смысл
- Есть несколько одинаково валидных архитектурных вариантов
- Задача может затронуть платежи, авторизацию или удаление данных
- Не уверен в приоритете между скоростью и качеством

**Не спрашивай**, если:
- Это вопрос про синтаксис — открой документацию
- Ответ есть в скиллах проекта — прочитай
- Это микро-решение типа "назвать переменную X или Y"

## 3. Спланировать

Для задачи **больше одного файла или с миграцией БД** напиши план **до** кода:

```markdown
## План: [название задачи]

### Цель
Одна-две фразы о пользовательском результате.

### Затронутые модули
- [ ] БД (миграции)
- [ ] Server Actions / queries
- [ ] UI компоненты
- [ ] Страницы
- [ ] Внешние интеграции
- [ ] Тесты

### Изменения по файлам
| Файл | Действие | Что |
|---|---|---|

### Миграция БД (если есть)
SQL или описание. RLS-политики. Возможные риски.

### Тесты
Какие unit / integration / E2E добавляются.

### Риски
- Что может сломать существующий функционал
- Необратимые шаги (drop column, миграция данных)
- Что требует ручной проверки

### Оценка
S / M / L — на сколько часов.
```

План не должен быть длинным — 5–15 строк по делу.

## 4. Согласовать

Отдай план пользователю. Жди подтверждения. Только после "ок, делай" начинай код.

Исключения, когда не ждать:
- Чистый рефакторинг внутри одного файла
- Багфикс с очевидным решением
- Пользователь сказал "делай по плану, не спрашивай"

## 5. Сделать

### Порядок реализации

1. **Типы и схема данных.** Если добавляешь сущность — сначала миграция и тип в `src/types/`, потом всё остальное.
2. **Серверная логика.** Server Action, query, валидация Zod.
3. **UI.** Компоненты, страницы, формы.
4. **Тесты.** Минимум unit на бизнес-логику и Zod-схемы.

### Тактика мелких шагов

Не пиши 500 строк за раз. Работай шагами по 50–100 строк, после каждого:
- `npm run typecheck`
- запусти dev-сервер, открой страницу
- `npm run test`

### Когда застрял

Если что-то не работает 15+ минут:
- Откати к последнему рабочему состоянию (`git stash` или `git restore`)
- Перечитай задачу — точно ли двигаюсь в правильном направлении
- Прочитай документацию использованной библиотеки
- Если не получается — спроси пользователя, опиши что пробовал

Не комментируй проблему — реши или сообщи.

## 6. Проверить

Перед коммитом обязательно:

```bash
npm run lint
npm run typecheck
npm run test:ci
npm run build
```

`build` важен — он ловит ошибки SSR и App Router, которые не видны в dev.

**Пройди руками** новый функционал в браузере. Если фича про авторизацию — проверь оба сценария (залогинен/не залогинен). Если про оплату — успех и отмену.

### Чек-лист перед коммитом

- [ ] Линтер чист
- [ ] Типы проходят
- [ ] Тесты зелёные
- [ ] Сборка проходит
- [ ] Ручная проверка прошла
- [ ] Нет `console.log` от отладки
- [ ] Нет закомментированного кода
- [ ] Нет `any`, `// @ts-ignore` без обоснования
- [ ] Секреты не попали в код
- [ ] Миграция есть в `supabase/migrations/` (если меняли БД)
- [ ] Обновлены типы (`npm run db:types`)

## 7. Закоммитить

```bash
git add -p   # выбирай куски осознанно, не add . автоматически
git commit -m "feat(модуль): краткое описание"
git push origin feat/название-ветки
```

### Формат сообщений

```
тип(модуль): краткое описание

опционально — детали, что и зачем
```

Типы: `feat`, `fix`, `refactor`, `chore`, `test`, `docs`, `style`, `perf`.

Примеры:
- `feat(auth): add Yandex ID OAuth provider`
- `fix(payments): handle webhook idempotency for ЮKassa`
- `refactor(lessons): extract video player into shared component`

### PR

Создай PR с описанием:
- Что сделано
- Какие тесты добавлены
- Скриншоты (для UI)
- Чек-лист пройден

## Особые случаи

### Срочный хотфикс
Цикл сжимается до: понять → план в голове → код → ручная проверка → коммит. Но всё равно через ветку `hotfix/...` и PR.

### Эксперимент
Если задача исследовательская — ветка `spike/...`, не мерж в main, оставь как референс. Отдельный коммит-summary с выводами.

### Большая фича
Если не помещается в один день — разбей на подзадачи. Несколько PR в одну фича-ветку. Не таскай ветку неделями — будет ад с конфликтами.
