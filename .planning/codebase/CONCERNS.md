# Codebase Concerns

**Analysis Date:** 2026-05-23

## Context: This Is a Fresh Scaffold

The repository is essentially a starter skeleton: only ~13 source files under `src/`, a single migration covering the most basic tables, and only one trivial unit test (`src/lib/utils.test.ts`). No payment, video, email, OAuth, captcha, OAuth, Telegram, Sentry, rate-limiter, or content-protection code exists yet. The entire `src/server/`, `src/components/`, `src/hooks/`, `src/stores/`, `src/lib/yookassa/`, `src/lib/kinescope/`, `src/lib/unisender/`, `src/app/api/`, and all route groups are empty directories.

For that reason, this document is largely **forward-looking**: it lists the gaps that already exist in the scaffold plus the risk areas the team must enforce as code lands. Where present, real file:line references are given. Where the concern is "missing entirely," the recommended location is noted instead.

## Security Concerns

### Already-present risks

- `src/lib/supabase/client.ts:5-7`, `src/lib/supabase/server.ts:8-9`, `src/lib/supabase/middleware.ts:8-9` — All three use the non-null assertion `process.env.NEXT_PUBLIC_SUPABASE_URL!`. If the env var is missing the process will start but fail at the first Supabase call with a confusing error. (LOW) Action: validate env vars centrally at boot (e.g. a Zod-parsed `env.ts` module imported from `next.config.js` and from every entry point), and fail fast with a clear message.
- `.env.example:12` — `SUPABASE_SERVICE_ROLE_KEY` is listed without a guard rail in code. There is currently no helper that loads the service-role client; once one is added, it MUST live in `src/lib/supabase/admin.ts` (or similar) and be flagged `import 'server-only'` so that importing it from a Client Component fails at build time. (HIGH if added carelessly later.)
- `src/middleware.ts:9-19` — Matcher is broad and protects all non-static paths, which is correct. However `updateSession` (in `src/lib/supabase/middleware.ts`) only refreshes the session — it does **not** enforce auth. Protection of `/(app)` and `/(admin)` must be implemented per-layout. (HIGH if forgotten when those layouts are added.) Action: add `src/app/(app)/layout.tsx` and `src/app/(admin)/layout.tsx` that call `requireUser()` / `requireRole('admin')` and `redirect('/login')`.
- `next.config.js:22-34` — Good baseline security headers (HSTS, X-Frame-Options DENY, nosniff, Referrer-Policy). However there is **no Content-Security-Policy** header. (MEDIUM) Action: add a CSP that whitelists Kinescope (`*.kinescope.io`), Supabase (`*.supabase.co`), Yandex Metrika, ЮKassa widget origins, and `'self'` for everything else; consider `report-only` mode first.
- `next.config.js:5-15` — `images.remotePatterns` allows `*.supabase.co` and `*.kinescope.io`. Wildcard subdomains are acceptable here but verify these are the only image sources before launch. (LOW)
- `src/lib/auth/require.ts:35-49` — `requireRole` performs a DB round-trip per call. Acceptable for now, but cache per-request (e.g. via `React.cache` or per-request memoization) to avoid duplicate queries when both a layout and a child Server Component check roles in the same render. (LOW today, MEDIUM at scale.)
- `src/lib/auth/require.ts:44` — `roles.includes(r.role as never)` uses `as never` to bypass type checking. Fine functionally but is the only type-assertion in the codebase. Replace with a proper guard once `Database` types are regenerated and `user_roles.role` is typed. (LOW)
- `src/lib/supabase/server.ts:20-23` — Empty catch swallows cookie-set errors. This is the documented pattern when called from a Server Component, but logging the error at `debug` level when `NODE_ENV !== 'production'` would help future debugging. (LOW)

### Missing entirely (must exist before launch)

- **Rate limiting** — no `@upstash/ratelimit` or alternative anywhere in `package.json`. Security skill mandates 5/15min on login, 3/h on register, 3/h on forgot-password, 100/min on webhooks. (HIGH) Action: add `@upstash/ratelimit` + `@upstash/redis` (or Vercel KV) and wrap every public-mutation Server Action and Route Handler.
- **Captcha verification** — `NEXT_PUBLIC_YANDEX_CAPTCHA_CLIENT_KEY` and `YANDEX_CAPTCHA_SERVER_KEY` are defined in `.env.example:44-45` but no server-side validation helper exists. (HIGH before login/register/forgot-password ship.)
- **CSRF protection on Route Handlers** — Server Actions get origin checks automatically, but custom `app/api/*` Route Handlers do not. Once webhooks and OAuth callbacks are added, every state-changing handler must verify either a signature (webhooks) or `Origin`/`Referer` (browser-originating). (HIGH when API routes land.)
- **Audit log table & helper** — Security skill mandates an `audit_log` table; no migration creates it, no helper writes to it. (HIGH) Action: include `audit_log` in the next migration plus `recordAudit(action, entity, meta)` in `src/server/`.
- **Service-role boundary** — No `src/lib/supabase/admin.ts`. The moment any code needs to bypass RLS (e.g. webhook handler), there must be a single audited helper that imports `server-only`.
- **Cookie hardening verification** — Supabase SSR sets cookies with sane defaults, but the project explicitly requires `httpOnly`, `Secure`, `SameSite=Lax`. Confirm via a Playwright test inspecting `Set-Cookie` once auth lands. (MEDIUM)
- **`@/lib/env` validator** — No central env parser. Adding one with Zod (and the `server-only` package on the secret block) prevents accidental leakage to the client bundle. (MEDIUM)

### Content protection (Kinescope)

- No code for signed URLs, watermarking, or per-lesson video access exists yet. (HIGH before any paid lesson is published.) The security skill describes the required pattern (signed URL with 4h TTL, email watermark, never persist URL on the client) — implement before the first paid course goes live. Place under `src/lib/kinescope/` (currently empty).

### Storage protection (homework submissions)

## 152-ФЗ / Compliance

- **Data residency disclaimer is unaddressed in code.** The security skill notes Supabase region `eu-central-1` (Frankfurt) is formally outside РФ and "requires lawyer confirmation." No infra-as-code or documentation in the repo records the eventual region choice. (HIGH for launch) Action: document the chosen region in `docs/` and align Supabase project provisioning accordingly; if РФ-first storage is required, plan a hybrid where primary storage of personal data lives in a РФ-hosted Postgres mirror.
- **No consent capture mechanism.** No `consents` table, no migration for it, no UI component. Registration UI is unbuilt, so this is forward-looking. (HIGH before registration ships.) Action: add a `user_consents` table storing `purpose`, `version`, `accepted_at`, `ip`, `user_agent`. Block registration until ticked.
- **No account deletion flow.** `/profile/danger` does not exist; no `deleted_at` column on `profiles`. The skill specifies soft delete + 30-day cron + Storage purge. (HIGH before launch.)
- **No data-export endpoint.** `/profile/export` does not exist. 152-ФЗ requires giving users access to data held about them. (MEDIUM before launch.)
- **No privacy policy / offer pages.** No `/privacy`, `/terms`, `/offer` routes. (HIGH before launch.)
- **No РКН registration tracking.** Not a code item but the security checklist (`SKILL.md:297`) lists it; add to launch checklist in `docs/`.
- **PII in logs.** No logging infra yet, but enforce now: do not log `email`, `phone`, `telegram_id`, `ip` to anything but the audit log (which itself must have access controls).

## Payments (ЮKassa)

No payment code exists. All the following must be implemented carefully when M3 (payments) starts:

- **Webhook idempotency** — A `webhook_events` table with `UNIQUE (provider, external_id)` is required (security skill `SKILL.md:170-191`). No such migration exists. (HIGH) Action: add in the migration that introduces the webhook Route Handler at `src/app/api/webhooks/yookassa/route.ts`.
- **Signature verification** — Validate the HMAC of every incoming payload against `YOOKASSA_SECRET_KEY`. Reject with 401 on mismatch. (HIGH)
- **Replay protection** — Combine signature check with the idempotency table. Reject events older than a sensible window (e.g. 5 minutes) using the event's own timestamp.
- **Server-side price** — Never trust amount from the client. Pricing must be loaded by `plan_id` from a `pricing_plans` table. (HIGH — easy to get wrong.) Plans table not yet created.
- **Fiscalization (54-ФЗ)** — Ensure ЮKassa receipt items are populated. Add a sanity unit test that the receipt payload assembled before sending contains valid items.
- **Backup provider (CloudPayments)** — `.env.example:20-21` mentions CloudPayments; treat as second-priority but design the payment-creation abstraction to allow swapping providers per plan.
- **Tests for payments** — At minimum: unit tests on signature verification, idempotency-conflict path, price-from-DB enforcement; E2E "happy path" using ЮKassa sandbox.

## Performance / Scaling

The codebase is too small to have real bottlenecks yet, but the following pre-emptive concerns apply:

- **`src/middleware.ts` runs on every non-static request** and performs `supabase.auth.getUser()`, which hits Supabase. This is the Supabase-recommended pattern, but with 10k MAU at peak it will dominate Supabase auth quota. (MEDIUM at scale.) Action: monitor latency; consider Edge-runtime caching of the user object if Supabase exposes a verified-locally JWT path.
- **No `revalidate` / cache directives anywhere.** `src/app/page.tsx` is a Server Component with no `export const revalidate = ...`. Once `getPublishedCourses()`-style queries land, define ISR windows per route (e.g. landing courses list `revalidate: 300`). (MEDIUM)
- **Migration `20260522000001_init_base_tables.sql` index coverage:**
  - Has indices on `modules.course_id` (line 91), `lessons.module_id` (line 119), `user_roles.user_id` (line 52), and a partial index on `courses.published` (line 73). Good.
  - **Missing**: no `(course_id, order_index)` composite on `modules`, no `(module_id, order_index)` on `lessons` — these are the most likely sort orders and will save sort cost as data grows. (LOW today, MEDIUM at thousands of lessons.)
  - **Missing**: no `idx_lessons_published` partial index — public reads will scan the table once non-preview rows pile up. (LOW)
  - **Missing**: `courses.slug` and `modules`/`lessons` have no `slug` columns yet but the public URL design implies slugs are needed for SEO. (LOW design observation.)
- **No N+1 audit hook.** Once Server Components start calling Supabase, easy to drift into N+1. Action: enable Supabase request logging in dev and add a check to `npm run test:integration` later.
- **Image optimization.** `next.config.js:5-15` wildcards `*.supabase.co` and `*.kinescope.io`. Verify `<Image>` is used for all course covers (no plain `<img>` tags). The currently empty components directory will need this enforced once it fills up — consider an ESLint rule `@next/next/no-img-element`.
- **Video optimization.** Kinescope handles encoding/adaptive bitrate, but the player wrapper (not yet written) must lazy-load (e.g. dynamic import with `ssr: false`) to keep the lesson page TBT low.
- **`experimental.serverActions.bodySizeLimit: '5mb'`** in `next.config.js:18-20` — generous for forms but if homework uploads go through Server Actions instead of Supabase Storage directly, this becomes a memory pressure source. (MEDIUM — recommend uploading directly to Storage with signed POST URLs.)

## Fragile Areas

- **`src/types/database.ts`** is hand-stubbed (lines 1-18). Any code that begins to rely on `Database['public']['Tables']['x']` will silently get `never`. The first migration was already written but the generator was not run. (HIGH coupling between "migrate" and "regen types" — easy to forget.) Action: add a Husky `post-merge` hook that warns if `supabase/migrations/` changed without `src/types/database.ts` also changing, and/or run `npm run db:types` as part of `npm run db:migrate`.
- **`src/lib/auth/require.ts:44`** uses `r.role as never` to dodge the missing type. This works only because the cast disables checks; once the DB types are real, the assertion will become wrong and silently pass. Action: remove the cast and add a unit test that catches breakage.
- **Empty `Database` interface** combined with strict mode (`tsconfig.json:7`) and `noUncheckedIndexedAccess: true` (`tsconfig.json:10`) means a real generated `Database` will surface many new errors at once. Schedule a focused PR for the day after the first real `db:types` run.
- **Migration is hard-coded `_init_base_tables`** with a `2026-05-22` timestamp. Subsequent migrations must use UTC-timestamp prefixes as the database skill instructs (`SKILL.md:13-18`); review every new migration filename.
- **Empty route groups + middleware matcher** create a misleading sense of safety: a developer might assume that placing a file under `(app)/` makes it require auth. It does not — only an explicit `requireUser()` in `(app)/layout.tsx` (yet to be written) does. (HIGH coupling between convention and implementation.) Action: write `(app)/layout.tsx` and `(admin)/layout.tsx` *immediately* when those groups start receiving real routes, even if they only render `{children}`, with the auth guard included from day one.
- **`process.env.NEXT_PUBLIC_APP_URL`** is referenced in `.env.example:61` but not yet imported anywhere. Once it is used in absolute URL construction (Open Graph, email templates, ЮKassa return URLs), missing values will produce malformed URLs at runtime, not at boot. Centralize via the future `env.ts`.
- **`Toaster` from `sonner`** is mounted at the root layout (`src/app/layout.tsx:32`). Good. But ensure error toasts never echo back full server errors (which can leak PII / internal info). Wrap server errors in user-friendly messages in Server Actions.
